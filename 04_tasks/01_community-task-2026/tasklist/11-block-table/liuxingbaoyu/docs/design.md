# 稠密 block_table 地址翻译算子设计文档

# 需求背景（required）

## 需求来源

本需求来自 xLLM 2026 年 11 月社区任务“稠密block_table地址翻译算子”。实现分页 KV Cache 场景下的逐层物理页表转换，提供 Python/C++ 工程及配套自验证材料。

## 背景介绍

### 稠密 block_table 地址翻译算子开发

多轮对话、长上下文和批量推理需要在 Attention 调用前，将请求使用的逻辑 block table 转为各层物理页表。本算子输出地址元数据，不搬移 K/V 数据，也不执行 Attention 计算。

### 现有方案分析

任务书基线通过 PyTorch NPU 操作完成逻辑索引类型转换、索引安全处理、逐层查表、负值填充和形状恢复。本设计结合 Triton Ascend、原生 NPU Gather 与主机侧 C++ 调度，减少地址准备过程的调用开销和中间张量。

### 算子功能分析

| 参数 | 含义 | 数据类型 | 形状及约束 |
| --- | --- | --- | --- |
| X | 请求的逻辑页表，负值表示无效位置 | INT32 | 连续 `[R,C]`，R、C≥0 |
| M | 逻辑页到物理页的映射 | INT32 | 连续 `[B]` 或 `[L,B]`，B、L≥1，元素非负 |
| attributes | 算子属性 | Python dict | 空字典 |
| output | 各层物理页表 | INT32 | `[R,C]` 或 `[L,R,C]`，独立连续存储 |

X 与 M 位于同一 NPU，支持合法的非零 storage_offset。M 的一维形式表示单层映射，二维形式表示逐层映射，不进行隐式输入广播。

# 需求分析（required）

## 需求描述

实现 prepare/run 调用接口，对逻辑页表逐元素查找物理页号，并将负值位置统一转换为 −1。计算在调用时的当前 NPU stream 上执行，支持合法输入值更新和 prepared 对象复用。

## 需求拆解

1. 实现单层、多层逻辑页查表及负值哨兵处理。
2. 覆盖零请求、零列、非对齐形状、非零存储偏移和 INT32 边界。
3. 完成一次性输入校验，运行时读取当前 X/M，保持输入不变与输出独立。
4. 组织 Python 接口、主机侧 C++ 调度、Triton 核及原生 NPU Gather 调用。
5. 完成正确性、性能、双 stream、输出生命周期及内存回收验证。

# 详细设计（required）

## 算子分析

### 数学公式

设 X 的请求下标为 r、列下标为 c，层下标为 l：

```text
output[l,r,c] = -1             ，X[r,c] < 0
output[l,r,c] = M[l,X[r,c]]    ，X[r,c] >= 0
```

一维 M 使用 `output[r,c] = M[X[r,c]]` 的单层形式，负值处理规则相同。映射表可以包含重复物理页号，各逻辑位置分别输出对应值。

例如某层 M 为 `[3,0,6,1]`，逻辑页表为 `[0,2,-1]`，输出为 `[3,6,-1]`。

### 支持数据类型

输入和输出均为 `torch.int32`，查表保留整数原值，不经过浮点转换。物理页号支持 INT32 非负值范围，包括 2147483647。

### 支持形状

X 为 `[R,C]`，M 为 `[B]` 或 `[L,B]`，输出分别为 `[R,C]` 或 `[L,R,C]`。R=0 或 C=0 时返回形状正确的空输出。单个输入及输出的元素总数均不超过 2147483647。

## 算子实现

### 实现方案

整体分为 Python 接口、主机侧调度和 NPU 计算三部分。prepare 完成校验与执行元数据准备；prepared.run 按输入规模选择设备执行路径，分配新输出并下发计算。

小规模输入采用 Triton 融合查表与负值处理，控制启动和临时分配开销；大规模输入结合原生 NPU Gather 组织批量查表，由主机侧 C++ 扩展减少 Python 层多步调度。各路径执行相同的整数映射语义，按层数和页表规模组织并行工作。

#### 3.2.1 host 侧设计

`prepare` 校验输入数量、空属性字典、Tensor 类型、设备一致性、连续性和形状。通过一次性值域回读检查 M 非负、X 的非负元素小于 B，并检查输入及输出元素总数。

prepared 对象持有输入 Tensor 与固定形状、设备和执行元数据。运行时从当前输入组织设备调用，不保存由旧 X/M 值产生的索引或结果；输入值合法更新后直接参与下一次计算。

主机侧 C++ 扩展接收 Tensor 和调度参数，使用当前 NPU stream 组织原生算子调用及所需设备处理。地址翻译计算在 NPU 上完成，主机侧不计算或缓存输出结果。

#### 3.2.2 kernel 侧设计

Triton 路径按层与页表元素区间分配任务，读取逻辑索引、执行带有效范围保护的映射查表，再写入物理页号。负值位置输出 −1，尾部掩码避免越界访问。

原生 Gather 路径在设备侧准备安全索引，完成逐层映射，并对负值位置恢复哨兵。临时索引和掩码基于本次输入生成，控制临时张量规模和设备调用数量。

输出按连续布局组织，每个输出元素由唯一计算位置负责写入，两个输入均只读。

#### 3.2.3 接口与工程接入

工程提供以下接口：

```python
prepare(inputs, attributes) -> Prepared
Prepared.run() -> torch.Tensor
run(inputs, attributes) -> torch.Tensor
```

调用形式为 `prepare([X, M], {})`。直接 `run` 包含准备与执行，`Prepared.run()` 复用准备结果。以 `solution.py` 提供统一入口，配套 Triton 代码、C++ 扩展源码、构建配置、测试入口及依赖安装说明，按 xLLM NPU 算子工程组织交付。

#### 3.2.4 流、生命周期与内存

设备计算使用调用时的当前 stream，不绑定 prepare 时的 stream。调用方保持输入和存储在设备计算完成前有效，并保证跨 stream 数据依赖的执行顺序。

每次分配独立连续输出，输出与输入及其他调用的输出不共享存储。prepared 对象不保留历史输出，当次临时张量按设备执行生命周期管理，调用方释放输出并同步后回收活跃分配。

| CANN | 9.1.0 |
| 软件依赖 | Python、PyTorch、torch_npu、triton-ascend 的配套版本 |
| 主机扩展构建 | C++ 编译器、Ninja |
| 验证方式 | 构造地址元数据，不加载模型权重 |

## 算子约束限制

- 输入必须为两个同设备、连续的 INT32 张量，attributes 必须为空字典。
- X 必须为二维，M 必须为一维或二维，B 和 L 至少为 1。
- X 的负值均作为无效位置；非负值必须小于 B，M 的元素必须非负。
- 支持合法的非零 storage_offset，不支持非连续布局。
- prepare 后 shape、dtype、device 和合法值域保持约定，可更新 X/M 的值；改变形状等固定元数据时重新 prepare。
- 非法输入在 prepare 中抛出 TypeError 或 ValueError，输入不被修改，输出不复用输入存储。

## 精度标准/性能标准

| 验收项目 | 标准 | 标准来源 |
| --- | --- | --- |
| 正确性 | 提交实现和基线均与独立 CPU 标杆逐元素零差异 | 任务书精度要求 |
| 小规模性能 | X `[8,64]`、M `[8,1024]`，平均耗时≤75 μs | 任务书主性能目标 |
| 大规模性能 | X `[64,256]`、M `[32,4096]`，平均耗时≤60 μs | 任务书主性能目标 |
| 同机收益 | 基线减实现的均值差、中位数差均大于 0，配对均值差的 95% 置信区间下界大于 0 | 任务书计时协议 |
| 存储与流 | 当前 stream 正确，输入不变，输出独立，释放后活跃分配恢复 | 任务书工程及内存要求 |

功能测试覆盖全部 14 个正向输入、7 项非法输入及规定的补充检查，包括单层与多层、空行与空列、全负值、映射重复、非对齐形状、非零存储偏移、动态 X/M 和 INT32 输出上界。按任务书提供的功能检查入口执行并补齐其余必测项目。

性能按完整 `prepared.run()` 计时。实现与基线分别预热 50 次，交替测量 6 轮，每轮连续调用 200 次并在轮末完成设备同步，以该轮总墙钟耗时除以 200 得到单次耗时。计时包含 Python 提交、主机扩展调度、新输出和当次临时张量分配、设备执行及完成同步；输入准备与传输、prepare、一次性校验、CPU 标杆、工程构建和首次编译在计时范围外。

主性能用例按六轮单次耗时的算术均值判定固定上限，配对收益使用 10000 次共同重采样、随机种子 20261031 和线性分位数计算 95% bootstrap 置信区间。X `[32,255]` 与 `[32,256]`、M `[4,1021]` 的两个补充用例执行配对计时并提交逐轮结果。

大小两组性能输入分别测量预热后的 PyTorch NPU 活跃分配峰值，包含一次完整调用的新输出和当次临时张量，保留输入和 prepared 对象。两条 stream 各保留 3 份输出，验证互不共享存储且逐份正确；重复 20 次调用，释放输出并同步后检查活跃分配恢复。

自验证保存功能及泛化结果、性能原始数据、内存记录、实际依赖版本和源码版本，形成步骤说明、精度/性能/内存报告及日志。失败、中断或缺失必测项均返回非零退出码。

## 兼容性分析

对外保持统一 Python prepare/run 接口，Python、C++ 和设备计算路径遵循相同的 INT32、形状及负值处理约定。C++ 扩展按实际 PyTorch、torch_npu 与 CANN 配套环境构建，设备执行路径使用同一 NPU 和当前 stream。不需要 ACLNN 自定义安装包。
