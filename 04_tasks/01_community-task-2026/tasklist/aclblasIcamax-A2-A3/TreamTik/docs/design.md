# 需求背景（required）

## 需求来源

依据 CANN 社区任务《aclblasIcamax 算子开发任务书（Atlas A2/A3）》，在 [ops-blas](https://gitcode.com/cann/ops-blas) 提供单精度复数向量最大模索引算子。目标代码目录为 `blas/iamax/arch22/`，目标测试目录为 `test/iamax/icamax/arch22/`。本任务面向 Atlas A2/A3，与 950 平台任务区分。

## 背景介绍

算子读取复数向量，输出模最大的元素位置。例如输入 `[(3, 0), (2, 2), (-2, -2)]`、`incx=1` 时，比较量为 `[3, 4, 4]`，结果为 `2`。这里的模是 `fabs(real)+fabs(imag)`，相同最大值取最小的 1-based 逻辑索引。

沿用仓库的公开接口、handle、stream 和工作区约定。架构设计参考 `arch22` 的 `aclblasIsamax` 工程框架，以及 `arch35` 的复数归约语义；设备实现采用 A2/A3 支持的 Ascend C 向量指令与搬运接口，不依赖 arch35 专属寄存器或 SIMT 路径。

# 需求分析（required）

## 需求描述

```cpp
aclblasStatus_t aclblasIcamax(
    aclblasHandle_t handle,
    int n,
    const aclblasComplex* x,
    int incx,
    int* result);
```

复用 `include/cann_ops_blas.h` 的公开声明。`aclblasComplex` 的实部、虚部均为 FP32，交错存储，每个复数占 8 字节。输入 `x` 与输出 `result` 均为 Device 指针。接口在 handle 绑定的 stream 异步执行，调用方在读回结果前同步该 stream。

| 参数 | 含义与约束 |
| --- | --- |
| `handle` | 已创建的库上下文；空指针返回 `ACLBLAS_STATUS_HANDLE_IS_NULLPTR` |
| `n` | 逻辑复数个数；负数返回 `ACLBLAS_STATUS_INVALID_VALUE` |
| `x` | 正常计算时非空；正步长物理长度至少为 `1+(n-1)*incx` 个复数 |
| `incx` | 相邻逻辑复数的物理间隔；零或负数走快速返回，不反向遍历 |
| `result` | 一个 INT32 输出；任意路径均须非空，空指针返回 `ACLBLAS_STATUS_INVALID_VALUE` |

## 需求拆解

1. Host 校验参数，使用 int64 计算正常路径的 `(n-1)*incx`，超过 `INT32_MAX` 返回非法参数状态。
2. `n==0` 或 `incx<=0` 时，在关联 stream 写 Device `result=0`，返回成功且不读取 `x`。
3. 正常路径计算复数 1-范数，按最大值及最小逻辑索引归约。
4. 覆盖连续和正步长输入，并处理尾块、特殊值和跨核并列值。
5. 按任务书建立精确索引比对和逐性能用例判定。

# 详细设计（required）

## 算子分析

### 数学公式与特殊值

对逻辑下标 `i=0..n-1`：

```text
physical(i) = int64(i) * incx
score(i) = fabs(real(x[physical(i)])) + fabs(imag(x[physical(i)]))
result = 最早达到最大 score 的逻辑下标 + 1
```

`score` 使用 FP32 加法，保留加法溢出产生的 Inf。输出是逻辑索引，不是物理偏移。

比较语义对齐 Netlib BLAS 3.10.0 的严格大于才更新规则。若第一个逻辑元素的 `score` 为 NaN，输出固定为 1。其余 NaN 不参与竞争。多个 Inf、相等有限值以及正负零均选择最小逻辑索引。

归约候选保存 `(value,index)`，`index` 使用 0-based 逻辑下标。后续 NaN 和无效尾部的 score 置为 -1；有效 score 均大于等于 0，因此这些位置不会胜出。有效候选先比较 value，大值胜出，相等时小 index 胜出。全局首元素的 NaN 单独保留至最终输出判定。每个 tile 不以其第一个值初始化特殊值语义，避免局部 NaN 错误冻结该 tile。

### 支持数据类型和形状

| 对象 | 类型 | 形状 |
| --- | --- | --- |
| 输入 | COMPLEX64，实虚部为 FP32 | 逻辑 `[n]`，正常路径 `n>0, incx>0` |
| 输出 | INT32 | 一个 Device 标量 |

正常路径满足 `(n-1)*incx<=INT32_MAX`，地址及字节偏移运算继续使用 64 位类型。附件精度尺寸覆盖至 `2^20`，性能尺寸覆盖 `1..2^22`；这些是测试范围，不作为额外 API 尺寸上限。

## 算子实现

### 3.2.1 Host 侧设计

检查次序为：handle、负 n、result 空指针、快速返回条件、正常路径 x 空指针、正常路径索引范围。错误路径返回对应状态码，资源获取失败不进入正常计算。

Tiling 是 Host 根据长度和硬件资源确定核数、每核区间与每次搬运大小的过程。读取平台的可用向量核数，不写死固定核数。tile 容量采用满足 arch22 UB 预算的容量上限。Tiling 只传递路径、n、incx、每核逻辑区间、tile 容量和参与核数。

| 路径 | 选择条件 | 设计目的 |
| --- | --- | --- |
| 快速返回 | `n==0` 或 `incx<=0` | 仅写 0，不扫描输入 |
| 单核 | 小规模，按单核工作量与启动代价确定 | 减少跨核同步和摘要开销 |
| 多核连续、单阶段 | `incx==1` 且未达到两阶段条件 | 连续搬运、向量计算，核内候选经同步后归并 |
| 大连续、两阶段 | `incx==1` 且 `n>=2*8192*activeCores` | 交错扫描与独立小归并 kernel，避免扫描核等待最终归并 |
| 正步长 | `incx>1` | 按逻辑下标读取有效复数，避免复制完整稀疏跨度 |

参与核数 `activeCores` 由逻辑长度、每核工作粒度和平台可用向量核数确定，不按用例编号特判。连续路径以 4096 个复数为核数计算粒度，常规 tile 容量为 8192；大连续两阶段路径的 tile 容量为 8128。各容量均计入 arch22 UB 预算。常规多核路径按不重叠逻辑区间均分，连续路径以 4 个复数为分组粒度，正步长路径以 64 个复数为分组粒度，余数组交给前面的核。

工作区复用 handle 既有有效 workspace，每个参与核使用独占的 32 字节槽位保存局部最大值、精确 uint32 逻辑索引及首元素 NaN 标记，规模与参与核数成正比，不分配与 n 等长的中间数组。核间槽位按所用搬运和同步接口要求对齐。不同 handle 使用分离工作区；同一 handle 的调用按其绑定 stream 有序执行，不承诺同一 handle 跨 stream 重叠调用的工作区安全。

### 3.2.2 Kernel 侧设计

```text
Host 参数检查与分块
  ├─ 快速返回：Device result ← 0
  └─ 正常计算
      每核：GM → UB → Abs → PairReduceSum → tile候选 → 核候选
      单核：直接写索引
      常规多核：写每核候选 → 核间同步 → 指定核归并 → 写索引
      大连续两阶段：交错扫描 → 写每核候选 → 同流第二kernel归并 → 写索引
```

GM 为设备全局内存，UB 为核内片上缓冲。连续输入采用连续搬运；交错分量直接执行 Abs，再由 PairReduceSum 对每个复数的相邻实虚分量求和，无需额外实虚拆分缓冲。随后使用向量比较形成候选。tile 内最大值与最小逻辑索引使用同一有效元素掩码，确保分块不改变并列取首规则。

正步长路径按 `2*int64(i)*incx` 定位实部 float，紧邻位置定位虚部。优先批量搬运，不逐元素标量读取 GM 输入。小正步长采用连续物理跨度搬入，Abs 后按复数实虚相邻对求和，再在 UB 聚集有效逻辑 score；这样用额外带宽换取连续搬运。大正步长采用多 block DataCopyPad，每个 block 搬运 8 字节复数并按接口约束填充 UB 槽位，然后按相邻对求和并聚集；这样避免读取大量间隔元素。设计以 incx=2..8 与 incx>8 作为初始两类路径，分界由实际带宽和搬运开销复核，不构成性能保证。

当合法索引范围内的 DMA stride 超过接口可表示范围时，以 64 位地址划分可表达的批次，仍通过 DMA 搬运。输入跨度已由 Host 使用 int64 校验；每个批次和尾部均按真实有效元素数设置搬运参数。连续、大步长路径共用向量候选归约，大规模输入按可用核数和每核有效工作量充分展开。

UB 预算同时计入交错输入、比较值、索引、掩码与归约临时空间。输入队列使用双缓冲，预算按两个输入槽计算。PairReduceSum 完成后立即释放当前输入槽，让后续搬运与候选归约重叠。tile 容量向搬运及向量粒度对齐，剩余空间满足归约接口临时区需求。连续路径将每个 64 元素向量组的局部最大值及索引写入批缓冲，累计最多 16 个 tile 后统一归约，末批不足 16 个 tile 时立即归并。批缓冲仅对值通道比较，索引保留 uint32 位模式，不转换为 FP32 数值。

尾 tile 只搬运有效字节，避免读取输入边界之外的数据。补齐位置的 score 置为 -1，不用补零参与最大值比较。result 只写一个 INT32，采用合法短长度写回，避免按整搬运块覆盖相邻输出。

### 3.2.3 核间归并与同步

以下同步方案用于常规单 kernel 多核路径。每个参与核完成全部 tile 后，将一个候选写入独占 workspace 槽位。先完成写出和所需流水依赖，再执行 arch22 合法的全核同步；指定核在同步完成后读取全部参与核候选。最终先判断全局首元素 NaN，再按相同比较规则合并并写 `index+1`。

同步路径采用 AIV-only 执行配置，并使用 CANN 9.1.0 对应的核间同步和调度配置，保证参与核匹配。所有参与核均到达同一个同步点，不让部分核提前返回。同步槽位和候选在每次调用时完整更新，不依赖上次 workspace 内容。使用批调度避免多个流的部分核互相等待，具体接口和调度标记通过目标版本头文件、编译与真机专项验证。

单核路径不进入全核同步。所有路径退出前恢复所用向量 mask、同步及 ABI 要求的状态。流水通过队列或事件明确 CopyIn、Compute、CopyOut 的依赖；buffer 释放晚于最后一次消费者完成。

### 3.2.4 大连续输入的两阶段归约

当 `incx==1` 且 `n>=2*8192*activeCores` 时，第一 kernel 采用 8128 个复数的固定块。设核数为 `C`、块长为 `T=8128`，完整轮次数为 `R=floor(n/(C*T))`。核 `c` 在第 `r` 轮读取 `[ (r*C+c)*T, (r*C+c+1)*T )`，其中 `r=0..R-1`。这样每核每轮读取一个连续块，各核跨轮交错覆盖整个完整区域。

完整区域后的 `n-R*C*T` 个复数按 4 元素组均衡分给各核，最后一组只读取真实尾部。逻辑索引由轮次、核号、tile 内偏移或尾区起点映射得到，不把交错扫描位置当作全局索引。每核按递增全局逻辑索引处理自己的数据，因此核内相等值保留首个位置。

第一 kernel 保留双缓冲、PairScores 后释放输入槽以及最多 16 tile 的批量归约。每核完成后只写自己的 32 字节候选槽位，不进入常规 SyncAll，也不写最终 result。槽位中的 index 与 firstNaN 使用 uint32 保存，避免大索引转换为 float 后丢失精度。

第二 kernel 在同一个 handle stream 上启动，使用一个向量核读取所有参与核的候选。stream 顺序保证第一 kernel 的候选写入完成后才执行第二 kernel。若核 0 的首元素 NaN 标记置位，输出 1；否则先求全局最大 score，再在所有达到该 score 的核候选中选择最小全局 uint32 index，最后加 1 写入 Device INT32 结果。交错划分下较小核号不保证拥有较小索引，因此最终并列值显式比较候选索引。

两阶段路径将扫描与最终归并分离，代价是增加一次小 kernel 启动；常规及正步长路径保留单 kernel，避免对小工作量引入额外启动。两阶段路径的性能按一次 API 中两个 kernel 的耗时之和计算，不以首阶段时长代表完整调用。

### 性能采集方案

性能用例沿用附件 `gpu_baseline.csv` 的 200 条记录，全部 `incx=1`，n 范围为 `1..4194304`。以 GPU 标杆原始 `gpu_ms` 乘 1000 转为 us，再逐条比较 `NPU_us<=GPU_us*1.25`，不以全量平均倍率掩盖单例未达标。

使用任务书规定的 `msprof op --application`，保持默认 replay 模式。工具自带 5 次 warmup，之后每条用例至少 10 个有效样本，取算术平均。每次完整 API 涉及的全部 kernel 时长相加，核对 `OpBasicInfo*.csv` 的 `Task Duration(us)`、样本数和阶段覆盖。仅返回 SUCCESS 且采集完整的调用纳入统计。

```bash
msprof op --application="<icamax_test> --gtest_filter=<单条性能用例>" --output=<output>
```

测试程序与采集参数配合保证有效样本数，不把 `--launch-count` 当作完整 API 样本数。排除 Host 造数、Golden、H2D/D2H。附件 README 的 event 计时只作辅助观测；正式判定以任务书的 `msprof op` 为准。记录源码版本、库哈希、实际 CANN、设备、编译参数、采集命令、有效样本和异常情况。

### 验证顺序与材料

按单算子构建验证公开符号链接与 arch22 GTest 注册，先完成可执行基线。性能先建立全量基线，再对未达标项及相邻边界优化，保留代表性正确性检查；性能收敛后执行完整精度、专项及最终全量性能。使用独立插桩构建检查内存、同步和退出状态，结合退出码、逐用例日志、GTest XML 与 profiler CSV 判断结果。

本设计规定实现和验证方法，性能数值、精度通过数与验收状态由对应代码版本的自测报告给出。

## 兼容性分析

公开接口由各架构共用，不增加平行 API。实现与测试落在 arch22，通过架构分支选择；arch35 的路径保留。沿用仓库公开的 handle、stream 和错误状态约定，工作区按本设计复用，并遵循本任务的复数、NaN 与索引契约。
