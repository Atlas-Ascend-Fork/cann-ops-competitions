# Rosetta Flex ddG 端到端异构加速设计文档

## 需求背景（required）

### 需求来源

CANN 社区任务 2026，任务书《Rosetta Flex ddG 端到端加速开发（Ascend 950PR）》。本任务面向**整模块端到端异构加速工程**，要求在 24 核 CPU + 单卡 Ascend 950PR 上，完成抗体-抗原复合物 `BD-623`（420 残基）的 50 个单点突变自由能变化（ΔΔG）计算，计算规模为 \(50 \times 35 \text{ 轨迹} \times 35,000 \text{ 步 backrub}\)。

目标代码仓将按照社区要求提供完整的异构调度代码、NPU Kernel 及测试脚本（参考目录结构 `rosetta_flex_ddg/`）。

### 背景介绍

Rosetta Flex ddG 协议是蛋白质工程和抗体设计中的核心计算任务，用于评估突变对蛋白质结合亲和力的影响。当前基于纯 CPU 的开源方案（Rosetta `2026.29` 版本）在 48 核上运行该任务需 **15.46 小时**。该协议包含大量高并发、高吞吐的微观计算，如：

1. **蒙特卡洛 Backrub / Sidechain 采样**：每个突变 35 条轨迹，每条 35,000 步，涉及大量几何扰动与局部构象空间探索。
2. **能量评估与打分（Scoring）**：基于 `talaris2014` 力场，计算范德华力、静电力、氢键、溶剂化等多项相互作用，是典型的访存密集型与计算密集型并存的任务。
3. **构象优化（Packing & Minimization）**：Repack 侧链（`UseMultiCoolAnnealer`），以及对初始和终止构象执行带约束的 L-BFGS 最小化。

上述计算在传统 CPU 上主要依赖多核并行的指令级流水，但受限于内存带宽与核数，无法有效处理数千条轨迹的并行。通过将**能量网格计算、多体相互作用评估、并行轨迹 MC 步进**等计算卸载至 NPU（Ascend 950PR），并结合 CPU 进行拓扑准备与全局调度，可实现数量级的加速。

### 核心约束（不可修改红线）

1. **力场绝对锁定**：必须保持 `talaris2014` 力场（等价开启 `-corrections::restore_talaris_behavior true`）。
2. **采样预算不变**：`nstruct = 35`，`backrub_trials = 35000`，邻域 8 Å，`max_iter=5000`，收敛阈值 `1.0`。
3. **流程不可删减**：不得跳过初始最小化、WT/MUT 重排与后处理最小化，严格遵守官方 `ddG-backrub.xml`。
4. **硬件资源约束**：严格限定 24 核 CPU（`taskset -c 0-23`）与单卡 950PR。

## 详细设计（required）

### 总体架构

由于 Rosetta 原版是庞大的 C++ 单体系统，彻底重写不现实。本设计采用 **“Host 侧拓扑准备与调度 + NPU 侧高并发能量与采样加速”** 的异构流水线架构：

```text
┌────────────────────────────────────────────────────────┐
│ Host CPU (固定 24 核)                                    │
│ 1. 输入校验与 PDB/CSV 解析                               │
│ 2. 结合界面 8A 邻域 (bubble) 构建与拓扑分析              │
│ 3. 生成并调度轨迹 (35 tracks/mutation)                   │
│ 4. 输出结果解析、统计汇总与 GAM 重加权计算               │
└───────────────────────┬────────────────────────────────┘
                        │ 异步下发 / 批量聚合
┌───────────────────────▼────────────────────────────────┐
│ Ascend 950PR (单卡)                                     │
│ 1. 约束最小化算子 (L-BFGS, 部分下沉)                     │
│ 2. 能量与导数计算算子 (fa_atr, fa_rep, fa_sol, fa_elec)  │
│ 3. Backrub 构象扰动与 Metropolis 接受判定算子            │
│ 4. Sidechain Packing (基于旋转异构体库的离散搜索)        │
└────────────────────────────────────────────────────────┘
```

### 异构拆解与算子设计

#### 1. 能量与导数计算（NPU 侧核心）
- **原理**：`talaris2014` 包含长程静电、范德华、溶剂化等，需基于邻接表（Neighbor List）计算原子对相互作用。CPU 上通常使用空间网格（Spatial Grid）加速。
- **NPU 设计**：
    - **邻接表重建**：将 8 Å 范围内的原子对打包为 flattened 的一维索引张量。若步长内跨越较大，考虑增量更新或局部重建。
    - **并行打分 Kernel**：将原子对作为线程/Block 维度，向量化计算 \(r_{ij}\)、\(\frac{1}{r_{ij}}\)、\(\frac{1}{r_{ij}^{12}}\)、\(\frac{1}{r_{ij}^6}\)。在 Vector/Cube 中融合计算 `fa_atr`、`fa_rep` 等。
    - **导数累加**：计算出的力（梯度）需通过原子索引进行规约（Atomic Add 或通过分离的规约 Buffer）。由于原子数量（420 残基 × 15 原子 ≈ 6300 原子）相对较小，可将其全部驻留至 950PR 的高速缓存或 UB 中，避免反复访存 GM。

#### 2. Backrub 蒙特卡洛采样（NPU 侧）
- **原理**：每步 MC 包含随机挑选 Pivot、调整主链二面角、侧链碰撞检测、能量差分接受判定（\(e^{-\Delta E / kT}\)）。
- **NPU 设计**：
    - **批量采样（Batch MC）**：将 35 条轨迹打包成一个 Batch 同时送入 NPU。利用 NPU 的并行性进行“随机数生成 - 构象更新 - 局部能量评估 - 接受判定”的批量处理。
    - **能量差分计算**：每步仅改变少数残基的构象，因此仅需计算**局部残基的 Delta Energy**（通过提取局部邻接表），显著降低每步的计算量，实现极高吞吐。

#### 3. 最小化 (L-BFGS)
- 纯 L-BFGS 迭代依赖历史步长和曲率信息，包含大量标量控制流（Armijo 条件判断）。
- **NPU 设计**：采用 **Host 侧控制流 + NPU 计算梯度** 的模式。Host 执行 L-BFGS 逻辑控制，每次迭代将当前构象下发，NPU 并行计算所有原子受力并回传，Host 计算方向和步长。对于 24 核 CPU 而言，此部分通信开销极小。

#### 4. Sidechain Packing (Repack)
- **原理**：给定骨架，遍历旋转异构体库（Rotamer Library），求能量极小值组合（NP-Hard），通常使用模拟退火或贪心策略。
- **NPU 设计**：对于给定残基位置，并行评估多个 Rotamer 能量（计算任务并行度高），利用 NPU 进行批量 pairwise 能量矩阵计算。

### 工程实现与流水线设计

#### 1. 全量并行策略（24 核 vs 950PR）
- **任务单元**：以“一条突变的一条轨迹”为基本单元。
- **CPU 调度**：采用 24 个 Worker 进程（绑定 CPU）。主进程负责解析输入、管理任务队列。Worker 进程负责从队列中拉取轨迹，完成初始最小化，下发至 NPU 执行 MC 采样，然后执行后处理最小化，最后汇总结果。
- **NPU 调度**：为了充分利用 NPU 算力，避免单进程独占，采用 **Device Runtime (Device 侧多进程/多实例)** 或 **异步 Stream** 机制。由于 950PR 是单卡，将通过 Python/C++ 多进程，每进程创建独立的 Ascend Stream，将 Batch 内的 MC 采样异步下发到不同的 Stream 执行。

#### 2. 数据流与内存管理
- **轨迹本地驻留**：每个 Worker 在内存中维护当前轨迹的原子坐标、速度、邻接表。每次与 NPU 通信仅传输变化量。
- **不落盘中间态**：除最后的 `results.csv` 和 `run_summary.json`，轨迹的 `.db3` 和临时 PDB 必须通过流式管道传输，避免磁盘 I/O 拖慢性能。

#### 3. 数值一致性保障
- 本任务采用 Ascend C / Triton 编写运算 Kernel，为保证与 CPU 基线（FP64/FP32 混合）的统计一致性，原子对距离、求逆等底层数学函数（如 `exp`, `sqrt`）需替换为底层优化版并保证误差可控。在 Monte Carlo 能量差分中，采用 FP32 计算，但 `repack` 评估等关键环节保留 FP64 高精累加。

### 接口与输出规范
提供如下的统一入口脚本接口：
```bash
taskset -c 0-23 python3 run_flexddg_npu.py \
  --selected   mutations.csv \
  --pdb-dir    pdb_dir \
  --xml        ddG-backrub.xml \
  --out        results.csv \
  --summary    run_summary.json \
  --move-chain A \
  --nstruct    35 \
  --trials     35000 \
  --cpu-cores  24 \
  --device-id  0
```
输出严格包含 `results.csv` 和包含时间、commit 等信息的 `run_summary.json`。其中 `results.csv` 保证 50 行 22 列，且 `ddG_residual` 绝对值 ≤ 0.01。

### 自验策略
1. 使用官方脚本 `verify_bd623.py` 执行测试，生成包含 Pearson 相关性等分析的报告。
2. 针对负向边界场景（缺 PDB、列不齐、核数超限、采样数不足）进行人工验证，确保能正确报错退出。

### 兼容性分析与风险应对

- **原版 Rosetta 协议接入**：由于流程长，应先在 CPU 上跑通从头到尾的单突变，再逐步替换耗时组件为 NPU Kernel。
- **24 核严格绑定**：在 Python 启动脚本的首行通过 `os.sched_setaffinity` 强制绑核，防止调度器逃逸。
- **精度走偏风险**：蒙特卡洛算法对能量微小的数值差异较敏感。若 NPU 计算的能量偏差过大，可通过引入本地修正（如定期用高精度重算基准）来避免轨迹漂移。
